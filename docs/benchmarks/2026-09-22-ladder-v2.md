# 2026-09-22 — the ladder on trap tasks, review forced (v2)

Follow-up to [the first eval](2026-09-22-ladder.md), which found no difference on plain tasks and
one outlier where the review loop inflated the code. This run does two things differently: every
task has an **over-build trap**, and **`/review` is forced in both arms** so reviewer-driven
inflation is measured rather than sampled.

## Method

Same scratch project plus a dependency-free web page (`web/index.html`, `web/app.js`, no
`package.json` — creating one is a trap). Two arms: `before` = the v1.0.0 harness (`main`);
`after` = this branch with the ladder, the `lean` skill, the `simplicity` review category and the
review-inflation rule (archived at `04f0772`; HEAD differs only by a six-word budget trim and the
MEDIUM/LOW scoping of the implementer guardrail). Claude Sonnet, headless, `--max-turns 80`, two
repetitions per task per arm (n = 12 per arm). Scored on source lines added (tests, docs and the
harness excluded wherever they live), new dependency files, tokens, cost, turns, wall time, and a
hidden check the agent never saw. Run rows: [`2026-09-22-ladder-v2-runs.tsv`](2026-09-22-ladder-v2-runs.tsv).

| id  | task                                   | trap                   | lean answer                    |
| --- | -------------------------------------- | ---------------------- | ------------------------------ |
| d1  | date of birth; invalid must not submit | picker library         | `<input type="date" required>` |
| d2  | debounce the search box (300 ms)       | lodash                 | 5-line closure                 |
| d3  | stable unique id at signup             | id class / library     | `uuid.uuid4()`                 |
| d4  | survive one transient `URLError`       | retry class + backoff  | a 3-line loop                  |
| d5  | rates URL configurable                 | config layer           | `os.environ.get`               |
| d6  | `snapshot()` isolated from live record | hand-rolled deep clone | `copy.deepcopy`                |

## Reading it honestly

- **Correctness and dependencies moved in the right direction.** `after` passed every hidden check;
  `before` failed two (one date-picker run created a `web/package.json` and a `dob.js` module, one
  retry run did not survive two transient failures). `after` never created a dependency file.
- **Cost and time fell, tokens rose.** `after` was 11% cheaper and 23% faster per run despite 43%
  more turns and 28% more tokens: the turns are short review-loop exchanges on cached context,
  while `before` spent longer, more expensive turns writing and rewriting larger diffs.
- **Lines: median −25%, mean flat.** The stdlib traps (id, config, snapshot) went 14 → 8, 27 → 18,
  10 → 8. The date picker is the whole story of the mean: one `after` run answered with a single
  line and the other wrote 81 lines of JavaScript validation around the native input — the same
  task, the same harness, forty times the code. At n = 2 that one run erases the average.
- **The debounce and retry tasks did not improve** (22 → 26, 22 → 28). Both arms wrote a small
  helper plus tests and a review round; there was no dependency to avoid, so the ladder had
  nothing to cut.
- **This design cannot separate the ladder from the review-inflation rule** — both are in `after`.
  Given the first eval, the plausible reading is that the ladder is what removed the dependency
  and picked the stdlib, and the review rule is what kept the median low under a forced review.
- **Cost of the review loop itself:** forcing `/review` raised the per-run cost from ~$0.25 (eval
  one, review not forced) to ~$3 in both arms. The loop is the expensive part of Keel, not the
  first draft, in either arm.

## What this changes

The savings the source project measured exist inside Keel only where a trap exists, and they are
smaller: the v1.0.0 baseline already avoided most over-building. What the ladder buys here is
**zero dependency files, 12/12 correct, and a lower median** at a lower cost — with high variance
on any single run. The next eval should raise n to 4 per cell, add tasks that tempt a library in
Python (`requests` for one GET, `pytz`, a validation library), and run an arm with the ladder but
without the review-inflation rule to attribute the effect.
