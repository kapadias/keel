# 2026-09-22 — the decision ladder, before vs. after

The first ROADMAP WS7 behavioural eval: does the always-on decision ladder change what the agent
builds? Two arms of the same harness, same tasks, same model.

## Method

- **Project:** a scratch Python service (`app/users.py`, `app/rates.py`, `app/util.py`, pytest,
  `docs/STATUS.md`), committed on `main`, work on `feature/bench`.
- **Arms:** `before` = `.claude/` + `CLAUDE.md` from the v1.0.0 harness (`main`); `after` = the same
  from this branch (ladder in `00-core.md`, `lean` preloaded into `implementer`, `simplicity` review
  category, debt gate).
- **Tasks (4):** email validation in `signup()`; caching in `fetch_rates()`; a `group_by` helper; a
  `parse_duration("1h30m")` parser. Each prompt ends "Do not commit; do not push."
- **Runs:** headless `claude -p`, Claude Sonnet, `--permission-mode acceptEdits` with the tools
  pre-approved, `--max-turns 60`; two repetitions per task per arm (n = 8 per arm).
- **Scored:** source lines added (tests, docs and the harness excluded), total tokens (input +
  cache + output), cost, turns, wall time, and a **hidden pytest** per task the agent never saw.

## Result

| arm        | correct | src LOC median (mean) | tokens mean | cost mean | turns mean | wall mean |
| ---------- | ------: | --------------------: | ----------: | --------: | ---------: | --------: |
| **before** |     8/8 |             7.5 (8.4) |        545k |     $0.24 |       13.5 |       52s |
| **after**  |     8/8 |            8.0 (10.9) |        587k |     $0.51 |       12.4 |      112s |

Per task, source lines before → after: t1 `[6, 6] → [7, 25]`, t2 `[7, 6] → [6, 7]`, t3
`[8, 8] → [8, 8]`, t4 `[13, 13] → [13, 13]`. Raw rows: [`2026-09-22-ladder-runs.tsv`](2026-09-22-ladder-runs.tsv).

**Reading it honestly.** On these four tasks the ladder made no measurable difference: every run
in both arms was correct, and the medians are identical. Keel's v1.0.0 baseline was already lean
("minimum code", "surgical changes"), and none of the tasks had a real over-build trap — the
source project's headline gain came from a date picker (404 → 23 lines), and nothing here invites a
dependency. The one outlier (`t1-after-0`: 25 lines, 570 s, $2.43) is the full Keel loop doing its
job in the wrong direction: the run dispatched the reviewers, and the correctness reviewer's MEDIUM
findings (RFC 5321 length limits, punycode TLDs) pushed a six-line email check into a 25-line
validator. The ladder did not cause that; it did not stop it either. That is the finding worth
keeping: **the simplicity lens has to outrank a reviewer's "add a bound" reflex on trivial
surfaces, or review inflates what the ladder trimmed.**

Excluding the outlier, `after` is 8.7 lines mean, $0.23, 12.4 turns — within noise of `before`.

## What to run next

- Tasks with an over-build trap (a date picker, a retry wrapper, a config layer, a deep clone) and a
  JavaScript/TypeScript project, where "native platform feature" and "installed dependency" bite.
- n ≥ 4 per cell, and a run that forces the review stage in both arms so reviewer-driven inflation
  is measured rather than sampled.
